# 面向完整算法工程能力的开源项目调研

调研日期：2026-10-02。以下把已查阅的项目事实、选题判断和未完成的计划分开记录。
这是工程项目路线，不承诺 Star 数量、招聘结果或模型效果。

## 选择原则

先做能独立解决一个问题的小工具，再围绕一个领域完成数据、基线、微调、评测和部署。
每个项目都需要真实用户、复现入口、失败案例和明确边界。仓库数量不是主要成果指标。
后续项目名称为工作名，不代表已经创建或训练完成。

| [Qwen3-VL](https://github.com/QwenLM/Qwen3-VL) | 开放视觉语言模型及相关使用说明 | 可作为候选基础模型；具体版本、许可证和训练栈需在实验时锁定 |
| [Loghub](https://github.com/logpai/loghub)、[Loglizer](https://github.com/logpai/loglizer) | 分别提供日志数据集合和日志异常检测方法实现 | 参考公开日志任务与传统基线；不能假设日志天然附带图文配对标签 |

这些事实支持“可能值得做”的推断，不证明项目独创、需求规模或未来传播效果。
不以动态 Star 排名代替需求调研，也不把历史 issue 说成当前框架缺陷。

## 六个候选方向

| 候选 | 面向的使用者与问题 | 可展示的能力 | 主要成本／不足 | 判断 |
| --- | --- | --- | --- | --- |
| **VLM Data Doctor** | 微调工程师在训练前定位格式、图片、拆分问题 | Python、数据契约、质量控制、测试、文档 | 不能单独证明算法研究和训练能力；同类功能已有 | 先完成一个小而可用的版本 |
| **NetOps VLM Lab** | 网络运维研发希望联合日志和拓扑图定位故障 | NLP、传统 ML 基线、多模态、LoRA、评测、错误分析 | 数据构建和业务有效性最难；合成数据存在领域差异 | 主项目，投入最多时间 |
| **VLM Perf Lab** | 部署工程师需要了解质量、延迟、吞吐、显存之间的取舍 | 推理性能、量化、并发、训练扩展性、Profiler | 对实验公平性和硬件记录要求高 | 主项目稳定后形成独立工具／实验集 |
| 中文文档图表抽取基准 | 企业文档开发者想定位 OCR、表格和图表问答错误 | 多模态抽取、结构化输出、字段评测 | 竞争多，数据许可和评测规范工作量大 | 网络运维方向没有可用数据时的备选 |
| 轻量中文 RAG 问答应用 | 知识库开发者需要检索与生成系统 | RAG 工程、服务集成 | 普通演示同质化，难证明训练与优化能力 | 作为领域项目组件，不单独优先建仓 |
| 从零实现大模型训练框架 | 学习者希望理解训练系统 | 深度学习与系统原理 | 维护量大、现有框架成熟、短期用户价值难验证 | 可做教学实验，不作为首个主打产品 |

## 项目一：VLM Data Doctor

当前仓库已实现的是数据预检，不是训练框架。第一阶段验收：

1. 新用户可以在 CPU 环境按 README 安装并运行正常／异常样例。
2. 错误定位到行与字段，报告可被 CI 使用，输入文件不被修改。
3. 对漏检、误报和不支持的格式有具体说明。
4. 获得至少三位独立使用者的实际反馈后，再决定扩展哪些规则；目前没有此类反馈。

后续若做“数据清洗提升训练效果”实验，应固定基础模型、训练预算与测试集，分别训练
原始数据／检查后人工修订数据，报告过滤比例、指标变化与失败案例。
静态检查通过率不能替代这项实验，也不能直接换算为节省的费用。

## 项目二：NetOps VLM Lab（计划）

输入是公开或自行生成的日志、拓扑图及任务描述；输出是故障类别、相关设备／链路和证据。
先定义可验证的分类和定位任务，再考虑自然语言解释。初期无需 Agent 自动操作真实网络。

数据方案：

- 自行构建小规模可复现拓扑与故障生成器，输出拓扑图、日志和结构化真值。
- 先人工检查约 100 个样例，确认任务可解、标签准确、图文均有必要，再扩展规模。
- 按拓扑族、模板和数据来源分组划分集合，并公开生成种子和拆分清单，避免仅随机拆行。
- 可参考有明确许可的公开日志，但逐个核实数据集用途和再分发条件；不要复制企业内部资料。
- 合成数据结果只能表明在该生成分布上的表现。真实场景能力需额外获得可合法使用的数据验证。

算法对照：

1. 规则方法及 TF-IDF + 朴素贝叶斯／逻辑回归，建立文本任务基线。
2. 基础 VLM 的零样本或少样本结果，固定提示词与评测配置。
3. LoRA 微调；选取适合任务的模型规模，锁定模型 revision、训练栈与随机种子。
4. 消融：仅日志、仅拓扑、日志 + 拓扑；微调前后、不同数据质量与规模。
5. 报告 macro-F1、设备／链路定位准确率、无依据判断比例及分任务失败案例。

传统算法不应为覆盖名词而堆砌。选择基线时说明类别分布、特征表示、计算开销和局限。
只有复杂模型在同一评测口径下确实改进，才能说明额外复杂度的价值。

多卡实验：先验证单卡小数据训练，再开展同构四卡实验。固定有效 batch size，控制
精度、图像尺寸、token 长度和数据顺序；记录吞吐、峰值显存、通信时间和扩展效率。
一份 torchrun 命令或配置文件不算已完成分布式训练。

发布物应包含生成器、数据卡、基线、训练配置、评测入口、环境锁定、训练日志、模型卡和
失败分析。模型或适配器是否可再分发取决于所用基础模型与数据条款，不能仅凭代码 MIT 许可证判断。

## 项目三：VLM Perf Lab（计划）

沿用主项目工作负载，复用 vLLM 的基准工具，研究可复现的部署取舍。

- 同一设备、模型、精度与工作负载下比较并发、批处理和缓存等设置。
- 量化、模型规模变化必须同时报告任务质量，不能只报告 tokens/s。
- 指标：TTFT、TPOT、请求总时延的 p50/p95、吞吐、成功率和峰值显存。
- 记录 warmup、测量窗口、输入／输出长度分布、图片尺寸、实际成功／失败请求。
- 原始逐请求结果与汇总脚本一同保存，注明服务端版本、驱动和 CUDA 环境。
- A100 与 4090 属于不同硬件平台；显存容量、互联和功耗等差异需单独记录，不能把跨设备差值全归因于软件优化。
- 若没有功耗或实际账单测量，不宣称能耗和费用降低比例。

每个优化都应有假设、对照、Profiler 证据及质量回归检查。若只得到“不同参数下谁更快”的
表格，它主要体现评测能力；要证明优化能力，还需要有针对瓶颈的实现或配置改进及受控对照。

## 建议节奏与验收

以下以每周约 10–15 小时为规划假设，实际按数据和实验进度调整，不是交付承诺。

| 阶段 | 产出 | 可以检查的证据 |
| --- | --- | --- |
| 第 1 周 | 小工具可用版本与试用说明 | 安装、测试、CI、可复现问题样例 |
| 第 2–3 周 | 网络运维数据和传统基线 | 数据卡、拆分清单、人工审查、基线指标 |
| 第 4–5 周 | 微调与消融 | 可运行配置、真实日志、固定测试集、失败分析 |
| 第 6–7 周 | 单卡／四卡与推理实验 | 原始测量、Profiler 记录、受控对照 |
| 第 8 周起 | 用户反馈、文档、上游贡献 | 外部复现、真实 issue 修复、被接受的 PR |

## 如何让项目被使用，并成为可说明的作品

- README 开头说清“谁遇到什么问题”，提供一分钟示例和真实输出。
- 中英文说明、明确许可证、版本记录和简洁安装流程，降低试用成本。
- 先征集小规模试用，跟踪外部复现成功率、问题定位价值、回访和修复效率。
- 有实际结果后再整理技术文章；分享渠道应遵守社区规则，不批量宣传或要求互刷 Star。
- 给上游提交真实的最小复现、修复或文档改进。Fork 本身不能替代原创贡献或被合并的 PR。
- 能解释数据拆分、基线选择、损失函数、过拟合、误差来源和瓶颈，才形成可信的面试材料。
- 简历中的性能数字必须链接到可重复的实验；没有实测前只描述已交付功能。

研究型岗位、应用岗位与系统岗位关注点不同。这个组合覆盖共同基础，但不意味着短期内
达到每个方向的专家水平。开源成果也不能保证绕过某些岗位的学历硬性要求。
